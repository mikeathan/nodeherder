Spec 035 · services grouping, height cost and collapse

The problem with “one Services box”

If Services is a narrow section with one card per row, six integrations become six stacked cards (~700px). It does not overlap other sections — grid items never overlay — but it forces a tall row and leaves a gap beside it.

  • Height is the cost, not overlap. A tall section sets the row height; shorter neighbours keep their top alignment and leave whitespace below.
  • Narrow + full card bodies is the worst combination: one column, 2–3 rows per card.
  • Three-level hierarchy (page → section → type subgroup → card) adds headings without solving height.

What actually controls the space

  • Section width — Services can span two page columns.
  • Inner columns — 2, 3 or 4 cards per row inside that width.
  • Compact card bodies — max 2 rows, then “+N more”.
  • Collapse — one row header with count and worst status.
  • Split — user creates several service sections instead of one giant one.

Revised recommendation

  1. Every card belongs to a section, but Services is a wide section, not a narrow one. On desktop it spans two page columns and lays cards out in 3–4 inner columns. Six compact cards become two rows, roughly the height of one area with six device tiles.
  2. No internal type headings. A section is the only grouping unit. Grouping inside a section would be a third level and would not reduce height. Card icon, title and colour carry the type.
  3. Compact card bodies by default. Bins shows the next 2 collections, fuel the cheapest 2, weather now + high/low, alerts headline + expiry. “+3 more” is a hint, and the detail page has everything. Full lists belong in results, not Home.
  4. Collapse per section. The header keeps name, count and worst status (for example “1 alert · 2 stale”) and can collapse the body to one row. Collapse state persists. This is the safety valve for a large Services section and also works for areas.
  5. Split on demand, never automatically. A section overflow action offers “Split into sections by type”, creating Weather / Collections / Travel / Safety sections once. After that they are ordinary sections: reorder, rename, collapse, drag cards between them. No hidden regrouping later.
  6. Order inside Services is manual, with a sensible default. Active alerts first, then weather, air quality, collections, fuel, transport, energy. A user drag overrides it. Severity never silently reorders cards, so spatial memory holds; an active warning is surfaced by the section header status and the card itself.
  7. A tall section never covers another. Sections are top-aligned grid items. The remaining gap is honest whitespace. Dense placement (filling gaps) stays an optional toggle, off by default, because it sacrifices predictable order.
  8. One item: header stays, card does not stretch. Empty: header plus add-card state. Neither is auto-hidden or auto-deleted.

Will Services cover device areas?

No. It is a grid item, not an overlay. It can only make the row taller. With a wide section plus compact cards the height is comparable to a normal area.

Will services be grouped internally?

Not with headings. Types are visible on each card. If you want real grouping, split Services into several sections; that is the Home Assistant model and keeps one hierarchy.

What about 9+ services?

Collapse the section, split it, or set it to the compact density. There is no hard cap, but the section header reports the count so growth is visible.
