# IoT control center: discovery and research

Date: 2026-10-30 | Branch base: `05212756` (`origin/main`)

## Repository findings

- The device registry and exposed entities live in `backend/models/devices/` and the application store. `DeviceProcessor` and `DeviceLifetimeService` already own device updates, accepted-state ordering, automation delivery and sampled publication. Keep one authoritative device state and preserve events before sampling.
- `backend/internal/controllers/hub-controller.go` receives MQTT reports and publishes device commands to Zigbee2MQTT topics. `backend/internal/automations/action.go` likewise configures actions with `mqtt.MqttClient`. A new adapter cannot be fully integrated merely by introducing another connection manager: both command paths need explicit protocol dispatch and compatibility tests.
- `backend/internal/ws/eventhub.go` and `frontend/src/store/modules/ws/` provide the existing broadcast and Vuex hydration path. Existing entity controls are under `frontend/src/components/entity/`; their Zigbee assumptions must be examined before reuse.
- The external-integration runtime is oriented around HTTP provider operations and resources, not persistent physical-device transports. Its encrypted repository/keyring are useful prior art for key protection but reuse must not make device management dependent on that optional runtime's availability.
- Existing public device context and MCP routes require a separate exposure audit: adding new physical devices to existing stores may change data available on those endpoints even without adding a route.
- The current Devices screen already has `DeviceCard.vue`, `DeviceFilterBar.vue`, `ExposeRow.vue`, `ExposeControl.vue` and `useDeviceCommand`; prefer extending their existing presentation and confirmed-command model rather than creating a competing dashboard. `HubController.OnDeviceSetValue` and `MqttTriggerAction.Configure` currently route and validate through Zigbee2MQTT-specific topics and bridge metadata; both must change together for generic controls and automation.

## External evidence

- The [official ESPHome client connection sequence](https://github.com/esphome/aioesphomeapi/blob/main/aioesphomeapi/connection.py) sends an empty legacy authentication request when logging in and does not wait for its response, because modern firmware removed password authentication. Older firmware requires that request before authenticated operations. Native API sessions also need periodic ping/pong to detect stale connections. This integration currently supports an empty legacy password and the separately configured Noise key; a non-empty legacy password is not yet supported.

- [ESPHome native API](https://esphome.io/components/api/) uses a protobuf TCP protocol, default port 6053 and optional Noise encryption using a base64-encoded 32-byte key. Encryption configuration and actual device support must be verified, not inferred from the IP address.
- [mycontroller-org/esphome_api](https://github.com/mycontroller-org/esphome_api) documents connection, commands and state subscription and uses Apache-2.0 licensing. The previously viewed main-branch module declared Go 1.21, but the downloaded v1.4.0 release declares Go 1.26; NodeHerder targets Go 1.24.8. Compatibility must be verified rather than inferred. The repository reports a small maintainer/community footprint. The user selected a patched v1.4.0, but cancellation, concurrency, message coverage, reconnection and Noise behavior still require verification before deployment. The supplied firmware's protocol version and actual entity inventory remain unverified.
- The latest GitHub release checked is [v1.4.0](https://github.com/mycontroller-org/esphome_api/releases/tag/v1.4.0), published 2026-07-18. Its versioned `pkg/client/client.go` registers the response waiter before sending, correcting an apparent race in the web-rendered main-branch source. It still uses `net.DialTimeout`, exposes `Close` that waits for a disconnect response, and reads/writes `lastMessageAt` across client paths; cancellation, shutdown and concurrency need isolated verification against this exact version before dependency selection.
- **Local fake-peer evaluation:** on 2026-10-30, isolated tests of `esphome_api@v1.4.0` and Go 1.26.1 found an invalid-key socket leak, a race in `LastMessageAt`, and process termination on a malformed plaintext frame length. See [client-evaluation.md](client-evaluation.md) for commands and limits. These are blockers to adopting the library unchanged. The temporary loopback-only test is `/private/tmp/nodeherder-esphome-eval/client_test.go`; no device was contacted and no production dependency was added.
- A second candidate, [go-aioesphomeapi](https://github.com/flavio-fernandes/go-aioesphomeapi), documents a context-bound Noise transport, simulator and explicit support matrix but says it is untagged and covers only a subset of the protocol. Its `go.mod` requires Go 1.25.12 while this project declares Go 1.24.8; GitHub reports GPL-3.0 licensing. No project license file was found at the repository root. It is not selected: toolchain, licensing, unsupported entity coverage, maintenance and independent tests must be resolved first. Its README and support matrix are upstream claims, not NodeHerder validation.
- **Maturity requirement (user, 2026-10-30):** mature, stable production software is required; an interesting implementation or simulator is not enough. Repository searches did not identify a Go native API client meeting that standard with verified safety and breadth. [Richard87/esphome-apiclient](https://github.com/Richard87/esphome-apiclient) is MIT and has a v1.1.0 tag, but its repository was created 2026-03-28, last pushed 2026-03-31 and has little observable adoption; do not assume a tag proves stability. `go-aioesphomeapi` explicitly has no tagged release and a limited implemented slice; reject it for this requirement. [periph/home](https://github.com/periph/home) targets the device/server side and was last pushed in 2022, not an actively maintained replacement client. These are evidence-based screening results, not an exhaustive proof no other library exists.
- ESPHome's [aioesphomeapi](https://github.com/esphome/aioesphomeapi) is the maintained Python client used by Home Assistant, with regular versioned releases (v46.23.0 on 2026-10-26). It is a credible maturity benchmark, not a Go package. The user explicitly requires Go, so a Python companion process is excluded.
- A fresh GitHub search on 2026-10-30 found no independently verified mature Go native-API alternative. `mycontroller-org/esphome_api` has releases since 2022 and a 2026 update, but the tested v1.4.0 cannot meet the safety gate unchanged. The most practical Go-native investigation is to fix the demonstrated defects in a controlled patch, seek upstream integration, and run protocol, fuzz, lifecycle and compatibility tests against independent implementations; this produces a maintained Go implementation only if its ongoing ownership is accepted and verified. A fork is not automatically mature because its parent has a release history. ESPHome's [MQTT component](https://esphome.io/components/mqtt/) plus NodeHerder's existing Go MQTT client is an established alternative transport, but would require firmware/configuration changes and is not the requested native API.
- [Home Assistant's device registry](https://contributors.home-assistant.io/core/integrations/device-registry/) and [openHAB Things](https://www.openhab.org/docs/concepts/things.html) distinguish device identity, entities/channels and connectivity. [Zigbee2MQTT exposes](https://www.zigbee2mqtt.io/guide/usage/exposes.html) distinguish accessible state and writable properties. Apply those principles without copying either platform's framework.
- The [ESPHome LD2450 documentation](https://beta.esphome.io/components/sensor/ld2450/) describes X/Y in millimetres, with negative X to the left and positive Y away from the sensor. The manufacturer's [v1.5.0 no-BLE configuration](https://github.com/EverythingSmartHome/everything-presence-lite/blob/v1.5.0/everything-presence-lite-ha-no-ble.yaml) selects LD2450, and its [versioned radar configuration](https://github.com/EverythingSmartHome/everything-presence-lite/blob/v1.5.0/common/ld2450-base.yaml) declares three X/Y pairs in mm and active flags. Tracking options can disable individual values, publishing `NaN` or false. That source does not establish the exact settings, entities or behavior of the installed device. Do not infer target presence from zero coordinates or claim synchronized X/Y samples without evidence.
- For controls, the [WAI slider pattern](https://www.w3.org/WAI/ARIA/apg/patterns/slider/) specifies keyboard behavior and warns about touch assistive-technology support; a numeric alternative and keyboard testing are appropriate. [Vue performance guidance](https://vuejs.org/guide/best-practices/performance) recommends measuring update and list-rendering costs; introduce virtualization only if the real device count warrants it. Radar should also have a textual target list rather than relying on a visual plane alone.

## Architecture options

| Option | Benefit | Cost and fit |
| --- | --- | --- |
| Capability model only | Reuses generic entity controls | Does not solve transport lifecycle or commands; insufficient alone. |
| Statically registered protocol adapters | Isolates ESPHome sessions and routes commands by stable provider identity | Small interfaces and explicit registration; best fit if integrated with existing device ownership. |
| Full hexagonal rewrite | Strong boundaries | Large migration and risk to existing automation/device contracts; reject for this scope. |
| Event bus as separate truth | Loose producers and consumers | Risks ordering, duplication and disconnected state; retain existing lanes/event callbacks instead. |
| Runtime-loaded plugins | Third-party modules without recompilation | ABI, security and deployment complexity without demonstrated need; reject. |

Working direction: statically registered adapters with narrow optional interfaces, one existing device-state owner, and a shared command router used by UI and automations. Exact contracts, migration, key ownership and security boundaries require further verification before implementation.
